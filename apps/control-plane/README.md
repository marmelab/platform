# Control plane

Node 24 + TypeScript (run directly, without a build step, thanks to type stripping), Hono, `pg`, dockerode, MCP SDK (Streamable HTTP, stateless mode).

## Getting started

```bash
deploy/install.sh          # generates deploy/.env, starts the "plat" compose project, initializes the cluster, creates the admin
deploy/install.sh --seed   # same, then scripts/seed.ts: builders alice and bob, todo-app and notes-app deployed through MCP
```

The script is safe to rerun. On the first run it prints the admin's PAT (`admin@example.com`, configurable with `ADMIN_EMAIL=`) and also saves it to **`deploy/.env.local`** (gitignored):

```
PLATFORM_URL=http://api.localhost:8100/mcp
PLATFORM_ADMIN_EMAIL=admin@example.com
PLATFORM_TOKEN=plat_...
```

After a code change: `docker compose -p plat -f deploy/docker-compose.yml up -d --build control-plane` (the image also builds the admin console, `apps/admin`).

The shared Storage and pooler images (`supabase/storage-api`, `edoburu/pgbouncer`) are pulled by `docker compose`; the Realtime image is the upstream `supabase/realtime` with the patches of [`patches/realtime`](../../patches/realtime/README.md), built by `deploy/install.sh` when missing (`REALTIME_BUILD=1` to rebuild). The per-app images (`GOTRUE_IMAGE`, `POSTGREST_IMAGE`) are pulled by the control plane when missing: in the background at startup, and before creating a container (concurrent provisionings share one pull). A failed pull (registry unreachable, Docker Hub rate limit) fails the provisioning with the registry's error.

## MCP

- URL: `http://api.localhost:8100/mcp`. Credentials: an OAuth access token (app builders sign in through the browser from Claude Code, see [Browser sign-in for Claude Code](#browser-sign-in-for-claude-code-oauth)), or a PAT (admins, scripts, tests), in `Authorization: Bearer <token>` or, for a PAT, in `X-Platform-Token: <PAT>` (what the plugin sends: an empty value counts as none).
- Claude Code without the plugin: `claude mcp add --transport http platform http://api.localhost:8100/mcp` (browser sign-in from `/mcp`), or with a PAT `claude mcp add --transport http platform http://api.localhost:8100/mcp --header "X-Platform-Token: $PLATFORM_TOKEN"`. A static `Authorization` header also works, but Claude Code then never falls back to the browser sign-in.
- Tools: `whoami`, `list_apps`, `get_app`, `create_app`, `create_deploy_token`, `link_repo`, `apply_migrations`, `execute_sql`, `create_deployment`, `finalize_deployment`, `begin_release`, `finish_release`, `list_deployments`, `rollback`, `set_secrets`, `list_secrets`, `list_members`, `add_member`, `remove_member`, `stop_app`, `start_app`, `delete_app`, `list_backups`, `create_backup` (owners and admins, see [Backups](#backups)), `list_schema_changes`, `get_logs`, `list_auth_users`, `invite_user`, `delete_user`, `ban_user`, `unban_user`, `configure_auth`.
- `whoami` also returns `credential` (`oauth`, `pat` or `deploy`: how this session authenticates), `direct_deploy` (whether this user may publish directly: always for admins, for everyone with `DIRECT_DEPLOY=everyone`), `direct_deploy_setting`, and `ci`: `{ uses, github_org }` derived from the first `CI_ALLOWED_WORKFLOWS` entry (`org/platform/.github/workflows/deploy.yml@refs/heads/main` gives `uses: org/platform/.github/workflows/deploy.yml@main`), or `null` when CI deployment is not set up. The plugin's `deploy` skill picks its path from these fields.
- Archives don't go through MCP: `create_deployment` returns a `PUT http://api.localhost:8100/uploads/<token>` URL (single use, 15 min) and a ready-to-use `tar` + `curl` command.

## Browser sign-in for Claude Code (OAuth)

App builders do not handle tokens (journey B1): the plugin's MCP server has no credential, Claude Code gets a 401 and signs the builder in through the browser, with the authorization of the [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) (OAuth 2.1, authorization code with PKCE). Claude Code stores the tokens in the system keychain and refreshes them.

**Authorization server: Supabase Auth.** A GoTrue dedicated to the platform's own accounts (`plat-oauth`, same image as the apps' GoTrue, `src/platform-auth.ts`) runs its OAuth 2.1 server: client registry, dynamic registration, pending authorizations with their PKCE challenge, single-use codes, consents, sessions and rotating refresh tokens. The control plane starts it like an app's GoTrue (orchestrator, replaced without downtime when its spec or image changes); its `auth` schema lives in the `platform` database, owned by the `platform_auth_admin` role; it is never routed publicly. Its JWT secret and database password are derived from the master key. Platform accounts stay in `users`: GoTrue only holds a **shadow user** per account that consented once (same id and email, no password, created through its admin API), and the consent page acts for it with a one-minute JWT. Sign-up is off.

**Client registration.** Claude Code supports dynamic client registration (RFC 7591), Client ID Metadata Documents and pre-registered clients. GoTrue implements dynamic registration (its `client_id` is a UUID, not a CIMD URL), so the platform uses it: nothing to configure per user or per machine. Only native clients are accepted: loopback redirect URIs (`http://localhost`, `127.0.0.1`, `[::1]`), public (`token_endpoint_auth_method: none`), authorization code and refresh token grants.

**Endpoints** (`src/oauth.ts`, on the API host; the rules are in `src/oauth-policy.ts`):

| Endpoint | What |
|---|---|
| `POST /mcp` without a valid token | 401 with `WWW-Authenticate: Bearer realm="platform", resource_metadata="<api>/.well-known/oauth-protected-resource/mcp"` (`error="invalid_token"` when a token was sent) |
| `GET /.well-known/oauth-protected-resource[/mcp]` | RFC 9728: `resource` = the MCP URL, `authorization_servers` = the API URL |
| `GET /.well-known/oauth-authorization-server` | RFC 8414: issuer (the API URL), endpoints, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]` |
| `POST /oauth/register` | dynamic registration, forwarded to GoTrue after the checks above (other metadata dropped) |
| `GET /oauth/authorize` | checks the client and the redirect URI (never redirects to an unknown one), then `response_type=code`, **PKCE S256 only** (GoTrue alone also accepts `plain`), `resource` (RFC 8707) equal to the MCP URL when present, `state` passed through; errors after the redirect URI is known go back to the client. A loopback redirect URI that only differs by its port from a registered one is added to the client first (RFC 8252 §7.3: Claude Code may pick another port; at most 10 per client). Then GoTrue records the request and sends the browser to the consent page |
| `GET/POST <studio>/_platform/oauth/consent` | on the Studio host, behind the platform's login (`/_platform/login`: password, company SSO, throttling; a disabled account cannot sign in). Shows "Allow access to your apps?", the client's name, "running on this computer", and the account's email, with Allow and Deny. The form is protected like the login form (Origin, `Sec-Fetch-Site`), the page is `no-store` and not framable. Approving records the consent in GoTrue; the next sign-in of the same account with the same client is approved at once, until the connection is revoked |
| `POST /oauth/token` | `authorization_code` (code_verifier and redirect_uri required; the code is single use, bound to the client, the redirect URI and the PKCE challenge, and refused more than **60 s** after the consent or for a disabled account) and `refresh_token` (rotation; reusing a refresh token older than the current one's parent revokes the whole family at once). `Cache-Control: no-store`; errors in the RFC 6749 shape (`invalid_grant`...) |

**Tokens.** Access tokens are GoTrue JWTs (HS256, `iss` = the API URL, `session_id`, `client_id`), valid **1 hour**; refresh tokens do not expire on their own. Each GoTrue session opened by a code exchange gets a row in `tokens` (`kind = 'oauth'`, `oauth_session_id`, `oauth_client_id`, the client's name as `name`, `last_used_at`): the admin console lists and revokes it like a PAT. `authenticate()` accepts an access token when its signature, issuer and expiry are valid, its row is not revoked, its GoTrue session still exists and the account is active; a refresh is refused (and the session ended) when the row is revoked or the account disabled. Tokens never appear in URLs, except the authorization code on the loopback redirect.

**Revocation.** Revoking a Claude Code connection (admin console, Tokens; API `DELETE /api/tokens/<id>`) revokes every connection of that account with that client, revokes the consent and deletes the GoTrue sessions (their refresh tokens with them), and revokes the deploy tokens minted from them: the next request gets a 401, Claude Code fails to refresh and asks to sign in again (with the consent page). Disabling an account ends its GoTrue sessions too, and every credential of a disabled account is refused at once. Deleting an account deletes its shadow user. Audited: `oauth_authorize` (`client_id`, `client_name`, `approved`, `remembered`), `oauth_connect` (code exchanged), `oauth_token_revoked`, `create_deploy_token`.

**Local installs.** Claude Code only sends token requests over HTTPS or to a loopback host, and `api.localhost` is not one: on a plain HTTP `*.localhost` stack, the metadata announce the token endpoint as `http://localhost:8100/oauth/token`, which Caddy routes to the control plane for that path only (`config.loopbackTokenHost`). In production (HTTPS), every endpoint is on the API host, and the OAuth endpoints refuse a request that reached Caddy over plain HTTP.

### Deploy tokens (`create_deploy_token`)

`platform-deploy` is a separate process: it cannot read the OAuth tokens Claude Code keeps in the keychain. `create_deploy_token(app)` returns a token (`plat_dep_...`) valid **15 minutes**, restricted to that app (`tokens.app_ids`) and to the tools `platform-deploy` calls (`tokens.scopes = {deploy}`: `whoami`, `get_app`, `apply_migrations`, `begin_release`, `create_deployment`, `finalize_deployment`, `finish_release`), and revoked with the credential that minted it (`parent_id`). `appForUser` and `appsForUser` hide the other apps, and the MCP server does not register the other tools (SEC-8, partly paid off). Any member of the app gets one: `platform-deploy check` (dry run) is open to every member, and the publishing tools apply `DIRECT_DEPLOY` to the deploy token as to any credential (`direct_deploy` in the result). A deploy token cannot mint another one. The skills pass it to `platform-deploy` in `PLATFORM_DEPLOY_TOKEN`; `PLATFORM_TOKEN` (a PAT) stays the alternative for admins, scripts, tests and CI outside GitHub.

## Releases, direct deployment and `DIRECT_DEPLOY`

A **release** groups the deployments (migrations, functions, frontend) of one publication. `releases.source` is `ci` (one GitHub Actions run attempt, through the CI API below: commit, run URL and GitHub actor from the OIDC claims) or `direct` (a PAT through MCP: the platform account in `created_by`). `get_app` returns the app's `last_release`, and `list_deployments` the `release_id` of each deployment.

Direct deployment through MCP: `begin_release(app, commit_sha?, reason?)` opens a release, its `release_id` is then passed to `apply_migrations` and `create_deployment` (`finalize_deployment` follows the deployment), and `finish_release(release_id, succeeded|failed)` closes it. Without `release_id`, each successful publication is recorded as its own finished release. `platform-deploy` with a PAT (`PLATFORM_TOKEN`) drives exactly this sequence, with the commit of the local checkout and `--reason`. A release can only be used by the app it belongs to, while `running`; `finish_release` through MCP only closes `direct` releases.

The platform setting **`DIRECT_DEPLOY`** decides who publishes with a PAT:

- `admins` (default when unset; **use it in production**): builder PATs are refused the publishing tools (`apply_migrations` without `dry_run`, `create_deployment`, `finalize_deployment`, `begin_release`) with an error that points to CI. They keep everything else (reads, `dry_run`, `execute_sql`, secrets, members, `rollback`, `stop_app` / `start_app`). Admins keep the publishing tools: their releases are flagged `admin_exception = true` (the audited exception of ARCHITECTURE §6.3, with an optional `reason` given to `begin_release`).
- `everyone`: every member of the app publishes with their PAT (the M3 model). `deploy/install.sh` writes `DIRECT_DEPLOY=everyone` into `deploy/.env` for local installs, so that the e2e suites, the seed (`platform-deploy` with the builders' PATs) and the direct path of the `deploy` skill work without GitHub.

The tools stay listed for builders; the refusal happens at call time, so that Claude gets the explanation.

## CI deployment API (GitHub OIDC)

The same operations as the MCP deployment tools, for GitHub Actions (called by `platform-deploy`, see [`packages/deploy-cli`](../../packages/deploy-cli/README.md), from the reusable workflow `.github/workflows/deploy.yml`), on `http://api.localhost:8100/ci/apps/<slug>/...`, authenticated by a GitHub OIDC token in `Authorization: Bearer` (`permissions: id-token: write`, audience = the platform API URL). No PAT and no long-lived secret in GitHub.

| Request | Mode | Body | Does |
|---|---|---|---|
| `GET /ci/apps/<slug>` | check | | `get_app`, plus `mode` and `check_reasons` |
| `POST /ci/apps/<slug>/migrations` | check if `dry_run: true`, else deploy | `{migrations, dry_run?, accept_lints?}` | `apply_migrations` (rejected lints: HTTP 422 with the same body as MCP) |
| `POST /ci/apps/<slug>/release` | deploy | | opens the run's release (idempotent per run attempt) |
| `POST /ci/apps/<slug>/deployments` | deploy | `{kind}` | `create_deployment` in the run's release (upload URL as in MCP) |
| `POST /ci/apps/<slug>/deployments/<id>/finalize` | deploy | | `finalize_deployment`, only for a deployment of the run's release |
| `POST /ci/apps/<slug>/release/finish` | any | `{status: succeeded\|failed, error?}` | closes the run's release |

The run's release is identified by the token's `run_id` and `run_attempt`: the client does not pass ids, and a token from another run cannot publish into it. Errors are `{error}` with 401 (token), 403 (workflow, repository, check mode), 409 (no release for the run, app stopped), 400 (invalid body, release already finished).

Every request checks, in this order:

1. the signature against the issuer's JWKS (`jose`, RS256; keys cached 10 min and refetched on an unknown `kid`), `iss` = `OIDC_ISSUER`, `aud` = `OIDC_AUDIENCE`, `exp` (30 s clock tolerance), and the GitHub claims the API uses;
2. `job_workflow_ref` against `CI_ALLOWED_WORKFLOWS`: this is what guarantees that the company checks ran, since editing the app repo's workflow does not change the reusable workflow it calls;
3. `repository_id` = the app's `github_repo_id` (`link_repo`), stable across renames. An unknown app and an app linked to another repository give the same 403.

Then the mode: **deploy** when `ref` = `refs/heads/<default_branch>`; **check** otherwise (pull requests, other branches), which only allows `GET` and migrations `dry_run`. A **stopped** app refuses every publishing request (409 `{"error": "APP_STOPPED: ...", "code": "APP_STOPPED"}`); `GET` and `dry_run` stay available.

Audit: CI actions are recorded with no `user_id` and `actor: github:<login>` in the details; `create_release` records the commit, run URL and actor.

## Schema changes outside releases

Every app database (and `template_supabase`) has two event triggers, `platform_record_ddl` (`ddl_command_end`) and `platform_record_drop` (`sql_drop`), from [`packages/sql/schema_changes.sql`](../../packages/sql/schema_changes.sql). They record each DDL command into `_platform.schema_changes`: time, transaction id (`xid8`), command tag, object type and identity, session role, `application_name` (`platform-migrations`, `platform-execute-sql`, `postgres-meta <version>` for Studio...). Temporary objects, extension members, and the sessions of `supabase_admin` (provisioning, Studio registration) and `app_<id>_auth_admin` (GoTrue's migrations at boot) are not recorded.

Protection: the schema, table, trigger functions (`SECURITY DEFINER`, `search_path = ''`) and event triggers belong to `supabase_admin`; the app roles have no privilege on `_platform` (not exposed by PostgREST either), cannot drop or disable event triggers they do not own, and cannot set `session_replication_role`. The SQL is idempotent and re-applied at every control plane start (to the template, briefly opened for connections, and in `syncAll` to every app) and at provisioning, which also re-enables disabled triggers. Limits: TECH_DEBT CP-15.

Release membership is decided by transaction, not by a session setting the app could forge: `apply_migrations` (MCP and CI) stores the transaction id of each committed batch in the migrations deployment's `manifest.txid`. A recorded change whose transaction is not one of them was made outside a release. `get_app` returns `schema_drift: { count, last_at, since }`: the commands recorded outside releases since the start of the last succeeded release (`since`, null if none; a single statement can record several commands, e.g. a table and its sequence), `null` if the app database cannot be read. `list_schema_changes(app, all?, limit?)` lists them, newest first; `all: true` lists every recorded change with `in_release` and `release_id`.

## Settings

Platform settings come from the control plane's environment (`deploy/docker-compose.yml`, values from `deploy/.env`), and can be overridden at runtime without a restart by a row of the `settings` table: `docker exec plat-control-plane node src/cli.ts set-setting <key> <value>`, `unset-setting <key>` to go back to the environment, `settings` to print the effective values. Both print `<key> set` / `<key> unset` first, then, for the keys that update the apps, a sync report (`auth service of 2/2 running apps up to date` for `smtp_*`, `company SSO of 1/1 apps up to date` for the SSO provider keys; exit code 1 when an app failed). They are read on every CI request and every MCP publishing call.

| Key | Environment | Default | |
|---|---|---|---|
| `direct_deploy` | `DIRECT_DEPLOY` | `admins` (`everyone` written by `install.sh`) | see above |

Stopped apps get it when started.

The control plane must reach the issuer's JWKS. Behind an HTTP proxy, Node's `fetch` needs `NODE_USE_ENV_PROXY=1` with `HTTPS_PROXY` in the control plane's environment.

## Apps

Each `<slug>` app is served at `http://<slug>.localhost:8100`: `/` (static, SPA fallback), `/auth/v1`, `/rest/v1`, `/functions/v1`, `/storage/v1`, `/realtime/v1` (M5, see [Storage and Realtime](#storage-and-realtime)).

Routing (`router.ts`): two generic Caddy routes serve every app, installed once at startup (`apps-by-host` on the public server, `apps-by-path` on the internal one). The slug comes from the host (`<slug>.<APPS_DOMAIN>`, matched against the slug pattern) or from the first path segment; the upstreams are `plat-<slug>-auth:9999` and `plat-<slug>-rest:3000`, the static root `/sites/<slug>/current`. Whether an app is served is decided on each request by a marker file in its sites directory: `.stopped` (maintenance, checked first), `.running` (served), neither (unknown app, 404). Creating, stopping, starting and deleting an app only writes or removes these markers: the Caddy config does not change, so these operations never reload Caddy. A Caddy reload drops the first request sent on a connection the old server had accepted but not used yet (a client's spare pooled connection), which made e2e suites fail with `fetch failed` (TECH_DEBT TT-4, paid off). The remaining config changes (the generic routes after an upgrade, the Studio route) are one `PATCH` of both servers' routes, guarded by Caddy's `ETag` and skipped when unchanged, so a control plane restart does not reload Caddy either. The first start after the upgrade from per-app routes removes the former `app-<slug>` routes in that same change.

## Storage and Realtime

One shared multi-tenant instance of each (M5, [architecture](../../docs/ARCHITECTURE.md) §3.2), one tenant per app, tenant id = slug (`src/storage-realtime.ts`). Nothing new for the app: supabase-js uses the same URL and anon key, and `get_app` is unchanged.

- **Storage API** (`plat-storage`, `supabase/storage-api`, `IS_MULTITENANT=true`): `/storage/v1/*` → `storage:5000`, with `X-Forwarded-Host: <slug>` set by Caddy (a value sent by the client is replaced) and matched by `REQUEST_X_FORWARDED_HOST_REGEXP`. The control plane registers the tenant with `PUT http://storage:5001/tenants/<slug>` (`apikey: STORAGE_ADMIN_KEY`): the app's JWT secret and keys, and its database as `app_<id>_storage_admin`: `databaseUrl` (direct, used for its migrations) and `databasePoolUrl` (through the [pooler](#connection-pooler), used for requests). Storage runs its own migrations (`storage.*`, owned by that role) in the app database at registration, and pending ones on the next request after an upgrade. The owner role is a member of the storage role: migrations and Studio create buckets (`insert into storage.buckets`) and policies on `storage.objects`. Files: volume `storage-data`, `tenants/<slug>/<bucket>/<object>/<version>` (`/data/storage` in the control plane). 50 MB per file, pool of 3 client connections per app to the pooler, released after a minute without requests; no image transformation, no S3 protocol.
- **Realtime** (`plat-realtime`, `plat/realtime:v<version>-platform<n>`: the upstream image patched so that the slot of Broadcast from Database is named per tenant, `SLOT_NAME_PER_TENANT=true`, [`patches/realtime`](../../patches/realtime/README.md); it connects to the app databases directly, not through the pooler): `/realtime/v1/websocket` → `realtime:4000/socket/websocket`, `/realtime/v1/api/broadcast[/...]` and `/realtime/v1/api/ping` → `realtime:4000/api/...`, with `Host: <slug>.realtime` (Realtime reads the tenant from the first label); any other `/realtime/v1/*` is a 404, so the tenant API, metrics and dashboard are never public. Tenant settings: the app's JWT secret, `postgres_cdc_rls` on the app database as `app_<id>_realtime` (`REPLICATION`, member of the API roles and of `supabase_realtime_admin`), publication `supabase_realtime` (owned by the app's owner role: `alter publication supabase_realtime add table ...` in a migration), slot `realtime_<id>_` (temporary, while `postgres_changes` subscribers exist). Realtime's tenant migrations need a superuser: a new tenant is created (`POST /api/tenants`, migrations run synchronously) with `platform_realtime_migrator`, which gets `LOGIN` and a one-time password only for that call (serialized), then the objects it created go to `supabase_realtime_admin` and the tenant is switched (`PUT`) to the app's role. After a Realtime upgrade that brings tenant migrations: `realtime-migrate --all` (CLI below; clients reconnect).
- **Provisioning** (`create_app`, `start_app`): roles and grants with the database (passwords in the app's encrypted secrets, generated for apps created before M5), then both tenants after GoTrue's migrations. At control plane start, running apps are registered in the background (both services may still be starting).
- **Stop**: maintenance on `/storage/v1` and `/realtime/v1` too (503 `APP_STOPPED`); the app's websockets are closed (`POST /api/tenants/<slug>/reload`), the sessions of its storage and realtime roles terminated with the others. **Delete**: the Realtime tenant first, then the Storage tenant and the files; the database's replication slots are dropped with it; the final backup adds `storage.tar.gz`.
- **Metadata databases**: `platform_storage` and `platform_realtime` (schema `_realtime`), each owned by its role (`STORAGE_DB_PASSWORD`, `REALTIME_DB_PASSWORD`), created by `init`.
- **Postgres**: `max_replication_slots=100`, `max_wal_senders=20` (`wal_level=logical` is the image default).
- **Studio**: the Storage browser works on the builder's own apps (its routes call the app through the internal gateway).
- Limits: 4 connections per Realtime tenant used in the last ~12 minutes (plus its walsender), no quota (TECH_DEBT SR-*, PG-5, PG-6).

## Connection pooler

One PgBouncer (`plat-pooler`, `pooler:6432` on the internal network, no published port) in **transaction mode** in front of the app databases (`src/pooler.ts`, `deploy/pooler/pgbouncer.ini`):

- **Who goes through it**: PostgREST (`PGRST_DB_URI` on the pooler, `PGRST_DB_PREPARED_STATEMENTS=false`) and Storage's requests (tenant `databasePoolUrl`). Direct: GoTrue (no idle connection, migrations with session locks), Realtime (session-bound: temporary replication slots, walsender), the owner role (migrations, `execute_sql`, Studio, `SUPABASE_DB_URL`), the platform.
- **Entries**: one `[databases]` entry per app (`app_<id> = host=db ... max_db_connections=POOLER_MAX_DB_CONNECTIONS`, 6 by default), generated from the `apps` table into `/data/pooler/databases.ini` (volume `pooler-config`, `%include`d by the pooler) and applied with `RELOAD` through the admin console (`pooler_admin`, `POOLER_ADMIN_PASSWORD`): at startup, at each provisioning and after `delete_app`, which also `KILL`s the app's pooled connections before dropping the database.
- **Authentication**: clients log in with their own role and password; PgBouncer reads the SCRAM secret with `auth_query` (`platform_pooler.get_auth()` in `postgres`, as `platform_pooler`, `POOLER_AUTH_PASSWORD`) and reuses the client's SCRAM keys to log in to Postgres. The function only returns `app_<id>_authenticator` and `app_<id>_storage_admin`: no other role (superusers, owners, Realtime, the platform) can log in through the pooler. The app roles' SCRAM secrets have a salt derived from the role and its password, so that the idempotent `ALTER ROLE ... PASSWORD` of each provisioning does not change them (a new salt would invalidate the keys the pooler caches from connected clients).
- **Pools**: 3 server connections per database and role (`default_pool_size`), 6 per app database (PostgREST's and Storage's pools: one never waits for the other's idle connections; Storage gives up connecting after 3 s), closed after 30 s idle (`server_idle_timeout`): an app without traffic holds no server connection.
- **PostgREST schema reloads**: `LISTEN` does not work in transaction mode, so PostgREST's channel is off (`PGRST_DB_CHANNEL_ENABLED=false`). The control plane listens to `pgrst` in each running app database instead (`src/pgrst-relay.ts`, one direct connection per running app as `platform_pgrst_relay`: `LOGIN` and `CONNECT` only, password derived from the master key) and relays each notification to the app's PostgREST container as a signal (`SIGUSR1`: schema cache, `SIGUSR2`: configuration). Notifications come from the image's DDL event triggers (Studio, `execute_sql`, functions) and from `apply_migrations`; the schema is also reloaded when the relay (re)connects. The relays live in the server process: the CLI's `start-app`, `stop-app`, `delete-app` and `restore-app` run in another one, so the server reconciles its relays with `apps.status` every 15 s (running: relayed; stopped or gone: closed), and a relay whose database no longer exists stops at once (logged once).
- **Measured** with 20 apps loaded at once (GoTrue, PostgREST, Storage, a Realtime client each; Postgres sessions per service at each phase): 75 s after the load, PostgREST and Storage hold 0 server connections (34 for PostgREST without the pooler, which keeps them forever); what remains is the relay (1 per running app) and Realtime (4 connections and a walsender per app for ~12 minutes, TECH_DEBT PG-5). The pooler itself uses ~3 MB.
- **Stop/start (B8)**: the database default `default_transaction_read_only` applies to new server connections; the sessions of the app's roles (the pooler's server connections included) are terminated when it changes, in both directions.

## Studio

`http://localhost:8100`: multi-head Studio (`apps/studio`), project ref = app slug, `studio_url` deep link in `get_app`. Platform login on `/_platform/login` (local account with password, or the company SSO: [Company SSO](#company-sso)), then forward auth (`/studio/verify` on the internal `:3001` listener): a builder only sees the apps they are a member of, an admin sees everything.

### No app key in the browser

Upstream Studio fetches a "temporary" key (`POST /api/platform/projects/<ref>/api-keys/temporary`, which the fork serves as the project's permanent `service_role` key) for the features that call the app's API from the browser. The policy refuses that route, admins included; these features go through Studio's server instead, with the same membership, CSRF and origin checks as the other project routes:

- Storage explorer: uploads (TUS proxy, `/api/platform/storage/<ref>/upload/resumable`) and empty folders (`POST /api/platform/storage/<ref>/buckets/<id>/objects/placeholder`), with the service key added server side.
- Auth > OAuth Apps and custom OAuth providers: `/api/platform/auth/<ref>/gotrue/auth/v1/admin/*` proxies the app's GoTrue admin API for `oauth/clients*` and `custom-providers*` only. The company SSO provider (`custom:company`, [Company SSO](#company-sso)) is read-only there (403, "managed by the platform": `configure_auth`). OAuth Server is off on the apps' GoTrue: its endpoints answer "not available on this platform".
- Realtime Inspector: `POST /api/platform/auth/<ref>/realtime-token` asks the control plane (`POST /internal/studio/realtime-token`, internal listener, bearer `PLATFORM_STUDIO_CONFIG_TOKEN`, with the user of the request's signed identity) for a JWT signed with the app's secret: role `service_role`, valid 10 minutes, for that app only. The control plane checks the account (active, member of the app or admin) and that the app is running, and audits `studio_realtime_token`. Listening stops when the token expires; start it again for a new one (accepted trade-off in TECH_DEBT).

### CSRF

Every `<app>.<domain>` is same-site with Studio, so its `SameSite=Lax` session cookie is also sent with requests made by an app's frontend. The forward auth (`/studio/verify`) and the `/_platform/*` routes therefore check the request's origin first (`crossSiteRefusal` in `src/studio/policy.ts`), before the session:

- a state-changing request (any method but `GET`, `HEAD`, `OPTIONS`: pg-meta queries, auth admin, content, login, logout) must carry `Origin: http://localhost:8100` (browsers send it on every non-GET request, same-origin included), and a `Sec-Fetch-Site` other than `same-origin` or `none` is refused;
- an API read (`/api/*`) with a `Sec-Fetch-Site` other than `same-origin` or `none` is refused;
- page navigations are not checked, so links to Studio from the admin console or from an app keep working.

Refusals are 403 (JSON on the API, text on `/_platform/*`). Unlike the admin console, Studio sends no custom header: vendored Studio would need a patch on every fetch, and the browsers' `Origin` and `Sec-Fetch-Site` headers are enough to tell Studio's own requests apart.

### Login throttling

Both logins (`/_platform/login` and the admin console's `POST /api/auth/login`) go through `src/login-limit.ts`, checked **before** the password: while locked, the right password is refused too (HTTP 429 with `Retry-After`; Studio shows the wait on its login page).

- **Per email**: the first 5 failures are free; the 6th locks the address for 30 s, and each further failure doubles the lock (1 min, 2 min...) up to 15 min, from any IP. A successful login clears the email's failures.
- **Per client IP**: same backoff from the 31st failure (people behind one company NAT share an IP), against password spraying over many accounts. A success does not clear it.
- Failures are forgotten after 15 minutes without a new failure. Counters are in memory (one control plane; a restart clears them, TECH_DEBT SEC-11).
- **Client IP**: the TCP peer, or the last `X-Forwarded-For` entry when the peer is Caddy (`TRUSTED_PROXIES`, default `caddy`, resolved on the Docker network). Caddy replaces any `X-Forwarded-For` sent by the client, and another container that calls the control plane directly cannot choose its IP with the header.

Studio and `execute_sql` connect as `app_<id>_owner`, which does **not** have `BYPASSRLS`. It owns the `public` tables, so their RLS does not apply to it (as for Supabase's `postgres`). In `auth`, it only reads `auth.users` and `auth.identities` (Auth > Users), through a `platform_owner_read` policy (`FOR SELECT TO app_<id>_owner`); every other `auth` table is denied. `register` (app creation, `syncAll` at control plane startup) re-applies the grants and recreates missing policies: after a GoTrue upgrade whose migrations recreate an `auth` table, restart the control plane (or re-run `create_app`) to repair them.

## App users (B5)

The app's own users (accounts of its GoTrue, not platform members) are managed by any member of the app, owner or collaborator, and by admins (`src/auth-users.ts`).

- `list_auth_users(app, page?, per_page?, filter?)`: `id`, `email`, `created_at`, `last_sign_in_at`, `invited_at`, `confirmed`, `banned`, `banned_until`, `providers` (how the user signs in, as in Studio: `email`, `custom:company` for the company SSO..., from `auth.identities`), newest first, with `total`; `filter` is a case-insensitive substring of the email. It reads `auth.users` as the owner role (as Studio's Auth > Users, through the `platform_owner_read` policy), so it also works on a stopped app.
- `invite_user(app, email)`: GoTrue creates the user (unconfirmed, `invited_at` set) and, with the platform SMTP ([Email](#email)), emails the invitation itself (`/invite`): the tool returns the user and `email_sent: true`, never the link. Without SMTP, it calls `/admin/generate_link` with `type: invite` instead, which returns the link without sending anything, and the tool returns that `invite_link` with `email_sent: false`, for the builder to hand over privately. The link is single use and valid 24 h (`GOTRUE_MAILER_OTP_EXP`). Opening it confirms the address, signs the person in and redirects to the app with the session in the URL fragment; the app then lets them set a password (`supabase.auth.updateUser`), unless it uses magic links. Inviting again a pending invitation sends (or returns) a new link, the previous one stops working; an address already registered is refused, and so is an address outside the app's `allowed_email_domains`. Links are built on the app's public `/auth/v1/verify` (`GOTRUE_MAILER_URLPATHS_*`).
- `delete_user(app, user_id | email)`: hard delete (`DELETE /admin/users/<id>`); rows of the app's tables follow their foreign keys to `auth.users`.
- `ban_user(app, user_id | email, duration_hours?)` (indefinitely by default) and `unban_user`: GoTrue's `ban_duration`. A banned user can no longer sign in nor refresh a session; access tokens already issued stay valid until they expire (1 h, TECH_DEBT CP-16).

Writes go to the app's GoTrue admin API directly on the `plat` network (`http://plat-<slug>-auth:9999`), with a `service_role` JWT signed by the control plane with the app's JWT secret and valid one minute: no key or secret is returned. They are refused on a stopped app (`APP_STOPPED`, `requireWritable`; its GoTrue is stopped anyway), and an unreachable GoTrue gives an explicit error. They are audited (`invite_user`, `delete_user`, `ban_user`, `unban_user`) with the acting user, the target email and user id (and `email_sent` for invitations), never the invite link.

## Email

**Platform SMTP.** One SMTP relay for the whole platform (the company relay, or Brevo, Scaleway TEM...), set by the `smtp_*` settings ([Settings](#settings)): environment defaults (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SENDER_EMAIL`, `SMTP_SENDER_NAME`) overridden by the `settings` table. It sends:

- the apps' emails, through each app's GoTrue (`GOTRUE_SMTP_*`): sign-up confirmation (U1), password reset (U4), invitations (B5), email change. Sender: the app's name and the platform sender address, unless the app overrides them (`configure_auth`). Templates: GoTrue's defaults (English), links on `<app URL>/auth/v1/verify` (`GOTRUE_MAILER_URLPATHS_*`, which would otherwise drop the `/auth/v1` prefix). GoTrue limits each app to 30 emails per hour (`GOTRUE_RATE_LIMIT_EMAIL_SENT`, its default) and a confirmation or reset to one per address per minute (`GOTRUE_SMTP_MAX_FREQUENCY`);
- the platform's own emails (`src/mailer.ts`, nodemailer): the abandoned-app notice to the owners ([Load metrics](#load-metrics)), the welcome email of an account created in the admin console (no password nor token in it), and the membership emails (see "Membership emails" under [Admin CLI](#admin-cli-inside-the-container)).

Without SMTP (no host or no sender address), GoTrue cannot send anything: every app auto-confirms its users (`GOTRUE_MAILER_AUTOCONFIRM=true`), `invite_user` returns the link, and the platform sends nothing. `get_app` and the admin console tell it (`auth.smtp_configured`); the SMTP host, user and password are never returned by an API.

**Local installs.** `install.sh` writes `COMPOSE_PROFILES=mail` and `SMTP_HOST=mailpit`, `SMTP_PORT=1025`, `SMTP_SENDER_EMAIL=noreply@platform.localhost` into `deploy/.env`: the `mailpit` service of the compose file (profile `mail`) catches every email, with a web UI and an API on `http://localhost:8025`, read by the e2e suites (`test/mailpit.ts`). Production installs set `SMTP_*` to the company relay and leave `COMPOSE_PROFILES` unset.

**Existing apps.** The GoTrue environment is part of the container's config hash (`orchestrator.ensure`): at the first control plane start after this upgrade (and after any change of the SMTP settings), each running app's GoTrue is recreated in the background with the SMTP, `GOTRUE_MAILER_AUTOCONFIRM=false` and the link paths, one app at a time, a few seconds without `/auth/v1` each. From then on, the apps' new users must confirm their address: an app whose sign-up flow expects a session right away must show "check your email", or its owner sets `email_confirmation: false`. Users created before keep their state.

**App auth policy (B6).** `configure_auth(app, ...)`, owner or admin, audited (`configure_auth`, with the changed fields `{from, to}`), refused on a stopped app (`src/app-auth.ts`, table `app_auth_config`; no row means the defaults). Only the fields passed change, and the app's GoTrue is recreated only when its environment changes (a few seconds); the tool returns the policy in effect, also in `get_app` (`auth`) and on the admin console's app page (read-only):

| Field | Default | GoTrue |
|---|---|---|
| `signup_enabled` | `true` | `GOTRUE_DISABLE_SIGNUP`; invitations still create accounts |
| `email_confirmation` | `true` | `GOTRUE_MAILER_AUTOCONFIRM=false` when the platform has SMTP (`email_confirmation_effective`); without SMTP, users are auto-confirmed whatever this says (a warning is returned) |
| `allowed_email_domains` | `[]`: any | GoTrue's `before-user-created` hook: `_platform.before_user_created(jsonb)` in the app database (owned by `supabase_admin`, executable by the app's GoTrue role, domains inlined after validation), enabled only when the list is not empty. It refuses (403, "Sign-ups are restricted to email addresses of: ...") sign-ups, invitations and future SSO accounts outside these domains (exact domain, case-insensitive; no subdomains). Users created before keep their access |
| `redirect_urls` | `[]` | `GOTRUE_URI_ALLOW_LIST`: the app's own `<app URL>/**` always, plus these (http(s), globs allowed, e.g. `http://localhost:5173/**`). A `redirect_to` / `emailRedirectTo` outside the list falls back to the site URL (`GOTRUE_SITE_URL`, the app's URL) |
| `sender_name` | the app's name | `GOTRUE_SMTP_SENDER_NAME` |
| `sso` | `null` | `{provider: "company"}`: the platform's company SSO as GoTrue's custom provider `custom:company` (not an environment variable: GoTrue's admin API), see [Company SSO](#company-sso) |
| `sender_email` | the platform sender | `GOTRUE_SMTP_ADMIN_EMAIL`. Builders may only use an address of the platform sender's domain (the relay's SPF and DKIM, no spoofed addresses); admins may set any address the relay accepts |

`null` resets `sender_name` / `sender_email`; a list replaces the previous one. Custom email templates and per-app SMTP servers are not supported (TECH_DEBT CP-17).

## Company SSO

One OpenID Connect provider for the company (Entra ID, Google Workspace, Okta, Keycloak...), configured once by an admin in the admin console (**SSO** screen, `PUT /api/sso`) or with the `sso_*` [settings](#settings). It serves two purposes:

**Platform logins (A7, `src/sso.ts`).** Studio's `/_platform/login` and the admin console's login page show "Sign in with `<sso_name>`" while SSO is active (enabled, with an issuer, a client id and a secret). The flow is the authorization code flow with **PKCE** (S256), **state** and **nonce**:

1. `GET /_platform/sso/start?next=...` (Studio host) or `GET /api/auth/sso/start` (admin host) reads the IdP's discovery document (cached 10 minutes; its `issuer` must equal `sso_issuer` exactly), and redirects to its authorization endpoint with `scope=openid email profile`. The state, nonce, PKCE verifier and `next` go into the `platform_sso` cookie, encrypted with the master key (AES-GCM), bound to the host that started the login, valid 10 minutes, `HttpOnly`, `SameSite=Lax` (sent back on the IdP's top-level redirect), path-scoped to the callback.
2. The IdP redirects to `<studio>/_platform/sso/callback` or `<admin>/api/auth/sso/callback` (the two **redirect URIs to register** for the platform's client). The callback deletes the cookie, compares the state (constant time), exchanges the code at the token endpoint with the verifier (`client_secret_basic`, or `client_secret_post` when the IdP only lists that), and verifies the ID token with `jose` against the issuer's JWKS: signature (asymmetric algorithms only), `iss`, `aud` (and `azp` with several audiences), `exp` (60 s tolerance), `sub`, and the **nonce**.
3. The email claim must be present, verified (`email_verified: true`, unless `sso_require_verified_email` is off) and in `sso_allowed_domains` (exact domains, when set).
4. The account: the one already linked to this IdP subject (`users.sso_issuer`, `users.sso_subject`); otherwise the account with that email, which gets linked at that first login; otherwise, with `sso_auto_create=developer` and on Studio only, a new developer account without password. An account linked to another subject of the same IdP is refused (an email reassigned at the IdP does not take over the account) until an admin unlinks it (user page, "Linked to an SSO identity", `PUT /api/users/<id> {sso_linked: false}`, audited `unlink_sso`). Disabled accounts are refused; the admin console only accepts admins (and never creates accounts).
5. A platform session as with a password (`sessions`, `platform_session` cookie, `SameSite=Lax` on Studio, `Strict` on the admin host), then a redirect to `next` (Studio) or `/` (console).

Every SSO login is audited: `login_sso` (`via`, `issuer`, `subject`, `linked`, `created`) and `login_sso_refused` (`via`, `email` when known, `reason`: `state_mismatch`, `no_pending_login`, `nonce_mismatch`, `invalid_id_token`, `email_not_verified`, `domain_not_allowed`, `unknown_user`, `subject_mismatch`, `account_disabled`, `not_admin`, `idp_error`, `token_failed`, `discovery_failed`...). Refusals are shown on the login page (Studio: 403 page; console: back to its login page with the reason).

**Password sign-in** stays available by default. With `sso_password_login=admins`, developers are refused password sign-in on Studio while SSO is active (checked after the password, so the answer tells nothing without it); admins keep their password as the break-glass access (an IdP outage, a broken configuration). The admin console's own login was already reserved to admins.

**PATs are unaffected**: MCP, the admin API and the CI API keep their tokens. A builder who only signs in with SSO needs no PAT: Claude Code signs them in through the browser, on the same login page, hence with SSO ([Browser sign-in for Claude Code](#browser-sign-in-for-claude-code-oauth)). The welcome email of a new account mentions SSO instead of the password when password sign-in is reserved to admins.

**Saving the configuration** (`PUT /api/sso`, admins, audited `update_sso` with the changed keys, the secret as `(changed)`, and `back_to_environment` for the keys unset): only the keys whose value in effect changes are written and audited (saving the screen unchanged writes nothing); a value equal to the environment's (or the default's) removes the override instead of storing it, so the Settings screen only lists real overrides. An empty discovery URL, or the issuer's default one, follows the issuer. Turning SSO off only changes `sso_enabled` (removed when the environment has it off): the provider settings and the secret are kept for a later re-enable, and the apps' `custom:company` provider is removed; `unset-setting` forgets them. When the result is enabled, the control plane fetches the discovery document first and refuses (400, previous settings put back) an unreachable one or one whose issuer differs. `GET /api/sso` returns the settings without the secret (`client_secret_set`), the redirect URIs to register, and the number of apps using company SSO.

**Company SSO for an app's users (U2, `src/app-sso.ts`).** `configure_auth(app, sso: {provider: "company"})` (owner or admin, audited, refused while the platform's SSO is not active) adds the company provider to the app's GoTrue as the custom OIDC provider **`custom:company`**, through GoTrue's admin API (`/admin/custom-providers`, GoTrue v2.196): issuer, the platform's client id and secret, scopes `openid email profile`, PKCE. No container restart. The app signs its users in with supabase-js:

```ts
await supabase.auth.signInWithOAuth({ provider: "custom:company", options: { redirectTo: window.location.origin } });
```

GoTrue redirects to the IdP, receives the code on `<app URL>/auth/v1/callback`, verifies the ID token against the issuer's JWKS, creates the account at the first login and redirects to `redirectTo` (within the app's URL or its `redirect_urls`). The app's policy applies to a new account, in this order: `signup_enabled: false` refuses it ("Signups not allowed for this instance", whatever the domain) and only lets existing (invited) accounts in, then `allowed_email_domains` refuses other domains (GoTrue's before-user-created hook, as for sign-ups). `get_app` (`auth.sso`) shows `effective`, the `callback_url` to register at the IdP for the platform's client (TECH_DEBT SSO-2), and the supabase-js call. `sso: null` removes the provider. Changing the platform's issuer, client, secret, name or switching SSO off updates (or removes) the provider of every running app that uses it (`apps_sync` in the response; CLI `set-setting sso_*` too); a stopped app gets it at start. GoTrue only accepts an HTTPS issuer on a public address (TECH_DEBT SSO-3). The client secret then lives in the app's `auth.custom_oauth_providers`, which the owner role (Studio, `execute_sql`) cannot read.

**Local mock IdP.** Local installs run a mock OpenID Connect provider (`plat-idp`, compose profile `sso-test` written into `COMPOSE_PROFILES` by `install.sh`, code in `deploy/idp/mock-idp.ts`): it signs in **any email typed into its form** (or passed as `login_email` by the tests), with client `platform` / `platform-secret`. Its issuer is `https://idp.sso.test:8443`, served on its own network `plat-sso-test` at a TEST-NET-2 address (GoTrue refuses private and plain-HTTP issuers), with a CA it generates at its first start; `install.sh` writes `SSO_TEST_NETWORK` and `SSO_TEST_CA_VOLUME`, so that every app's GoTrue joins that network and trusts that CA (never set them in production). The browser reaches its authorization endpoint on `http://localhost:8090`; the control plane reads its discovery on `http://idp:8090`. To try it, in the admin console's SSO screen: issuer `https://idp.sso.test:8443`, discovery URL `http://idp:8090/.well-known/openid-configuration`, client `platform`, secret `platform-secret`, enabled; then "Sign in with ..." on Studio as `alice@example.com`.

## Admin REST API

The admin console (`apps/admin`, [README](../admin/README.md)) and its API are served by the control plane on the admin host, same origin: `http://admin.localhost:8100` (`ADMIN_HOST`), API under **`/api`** (`src/admin/`). Same origin rather than `api.<domain>/admin`: no CORS to configure, and the session cookie stays host-only on the admin host. Caddy proxies the whole admin host to the control plane (route `admin`, installed at startup with the Studio route); on that host the control plane serves only the SPA (`ADMIN_STATIC_DIR`, built into the image) and `/api/*` (no MCP, CI API or uploads), and the API is not served on the other hosts.

**Authentication.** Admins only (`users.role = 'admin'`, active), checked on every request:

- `Authorization: Bearer <PAT>` of an admin (scripts, tests);
- or the platform session cookie: `POST /api/auth/login {email, password}` reuses the sessions of Studio's `/_platform/login` (`sessions` table, `platform_session` cookie, `SESSION_TTL_SECONDS`), refuses non-admins (403, no session), and sets the cookie host-only, `HttpOnly`, `SameSite=Strict`. `GET /api/auth/me` returns the identity, `POST /api/auth/logout` deletes the session. With company SSO, `GET /api/auth/sso` (public) tells the login page whether to show the SSO button, and `GET /api/auth/sso/start` / `/callback` open the same session ([Company SSO](#company-sso)).

**CSRF.** Every `<app>.<domain>` is same-site with the admin host, so `SameSite` does not stop a builder's frontend from sending requests with an admin's cookie. With the cookie (not with a PAT), the API refuses any request whose `Sec-Fetch-Site` is neither `same-origin` nor `none`, and every mutation (and the login) must carry `Origin: <admin origin>` and `X-Platform-Admin: 1`: a cross-origin page cannot send that header without a CORS preflight, which the API never grants. The SPA sends it on every request. Login is throttled as Studio's (see [Login throttling](#login-throttling)).

**Conventions** ([ra-data-simple-rest](https://github.com/marmelab/react-admin/tree/master/packages/ra-data-simple-rest)): `GET /api/<resource>?sort=["field","ASC"]&range=[0,24]&filter={...}` returns an array and `Content-Range: <resource> 0-24/<total>`; `filter={"id":[...]}` (getMany) and `filter={"<field>": value}` (getManyReference) are supported; `GET|PUT|DELETE /api/<resource>/<id>`, `POST /api/<resource>` return the record. Errors are `{message}` with 400 (validation, guard refused, e.g. last owner), 401, 403, 404, 405, 409 (conflict; `code: "APP_STOPPED"` for a write on a stopped app). Lists are filtered, sorted and paginated in memory except the audit log (SQL).

## Security linter

`packages/sql/lints.sql` and `lints_storage.sql` (ARCHITECTURE §7, `src/lint.ts`): rules rewritten from Supabase's [splinter](https://github.com/supabase/splinter) (its repository declares no license, so it is not vendored), keeping its lint names so that [its documentation](https://supabase.com/docs/guides/database/database-linter) applies. Run as the app's owner role. Exposed schemas: `public` and `graphql_public` (PostgREST's `PGRST_DB_SCHEMAS`).

| Lint (splinter number) | Level | Flags |
|---|---|---|
| `rls_disabled_in_public` (0013) | ERROR | table of an exposed schema without RLS that anon or authenticated can select, insert, update or delete |
| `policy_exists_rls_disabled` (0007) | ERROR | policies on a `public` table whose RLS is off |
| `security_definer_view` (0010) | ERROR | view readable through the API without `security_invoker` (bypasses RLS) |
| `auth_users_exposed` (0002) | ERROR | view or materialized view readable through the API that reads `auth.users` with its owner's privileges |
| `rls_references_user_metadata` (0015) | ERROR | policy that reads `user_metadata` from the JWT (users can change it) |
| `anon_security_definer_function_executable` (0028) | WARN | `SECURITY DEFINER` function of an exposed schema executable by anon (`/rest/v1/rpc`); trigger functions excepted |
| `authenticated_security_definer_function_executable` (0029) | WARN | same, executable by authenticated (and not anon) |
| `function_search_path_mutable` (0011) | WARN | `SECURITY DEFINER` function of `public` without a fixed `search_path` |
| `extension_in_public` (0014) | WARN | extension installed in `public` |
| `materialized_view_in_api` (0016) | WARN | materialized view readable through the API (no RLS) |
| `foreign_table_in_api` (0017) | WARN | foreign table readable through the API (no RLS) |
| `rls_policy_always_true` (0024) | WARN | permissive INSERT, UPDATE, DELETE or ALL policy for anon, authenticated or public that is always true |
| `public_bucket_allows_listing` (0025) | WARN | public Storage bucket with a broad SELECT policy on `storage.objects` (anyone can list its files) |
| `unindexed_foreign_keys` (0001) | WARN | foreign key without a covering index (INFO in splinter) |

| `no_primary_key` (0004) | INFO | table of an exposed schema without a primary key |

`apply_migrations` (MCP and CI) runs the rules in the migrations' transaction: a new ERROR (absent before the batch) rolls it back unless accepted (`accept_lints`, `.platform.json` `acceptedLints`). Each run is recorded in `lint_runs` (counts and lints): after every committed batch (source `migrations`, with its release), on demand (admin console "Run linter" and `POST /api/apps/<slug>/lint`, `manual`; CLI `lint-apps`, `manual` or `upgrade`), and by a sweep every `LINT_SWEEP_INTERVAL_HOURS` (6 by default, `scheduled`) that lints the apps not linted since, to catch changes made outside releases (Studio, `execute_sql`). Runs tied to a release are kept with it, the others 30 days (each app's latest run is kept). The admin console shows the latest run on the app page (Security linter tab, accepted ERRORs marked), a `lint errors` flag in the apps list (ERRORs of the latest run that no migration accepted) and the apps with such errors on the dashboard.

## Platform version, upgrades and TLS

- **Version.** The `VERSION` file at the repository root is copied into the image; at every start the control plane records it in `platform_versions` with the images of the platform's containers (`docker` labels `platform.service`) and the per-app images, when either changed (`src/version.ts`). The dashboard and `cli.ts version` show it.
- **Upgrades** (A8): `deploy/upgrade.sh`, see [docs/INSTALL.md](../../docs/INSTALL.md#11-upgrading-a8). The schema migrations are the idempotent `packages/sql/platform.sql` (and the template's DDL event trigger), run at every start. `recycle-apps` recreates the GoTrue and PostgREST containers whose spec or image changed (`--force`: all): `orchestrator.ensure` replaces a running container without downtime (a `<name>-next` container with the network alias `<name>` started next to the old one, the old one stopped once the new one answers its readiness check, `/health` for GoTrue and PostgREST's admin `/ready`, then renamed), under a cluster-wide advisory lock per container (the server's startup sync and the CLI never recreate the same one at once). The same path serves `configure_auth` and SMTP changes. Then Studio's `platform_owner_read` policies on `auth.users` and `auth.identities` (formerly TECH_DEBT PG-4), Storage's tenant migrations and the edge config are re-applied. `verify` checks the shared services and each app (containers, GoTrue `/health`, PostgREST `/ready`, the routes through Caddy's internal listener, the Storage tenant, the latest lint run).
- **Hosts and TLS** (A1, `src/tls.ts`, `router.ensureEdge`): `PLATFORM_DOMAIN` gives `api.`, `admin.`, `<slug>.` and the domain itself for Studio (each overridable: `API_HOST`, `ADMIN_HOST`, `STUDIO_HOST`, `APPS_DOMAIN`). The control plane owns the public server's platform part at every start: the API route's host, and with `TLS_MODE=acme` (or `internal`, Caddy's own CA) HTTPS on `PUBLIC_PORT` (443) with on-demand certificates (Let's Encrypt, `ACME_EMAIL`, `ACME_CA`), HTTP/1.1 and HTTP/2, and a redirect server on `HTTP_PORT` (80); with `TLS_MODE=off` (local installs) plain HTTP on `PUBLIC_PORT` (8100). Before requesting a certificate, Caddy calls `GET http://control-plane:3001/caddy/ask?domain=<host>` (internal listener only): 200 for the platform hosts and `<slug>.<apps domain>` of an existing app (stopped ones included), 404 otherwise. Changing the TLS settings reloads Caddy once (`/load`, skipped when unchanged).

## Backups

Backups and restore of the apps (M7, journey A4, `src/backups.ts`, `src/restore.ts`, `src/s3.ts`). Every backup is recorded in the `backups` table (app, slug, kind, status, start and end, size, location, files, manifest, error, author) and is one directory `<slug>-<UTC timestamp>/`:

| File | Content |
|---|---|
| `database.dump` | `pg_dump --format=custom` of the app database (schema, data, auth users, Storage metadata), run in the Postgres container so that it always matches the server (check it with `pg_restore --list`) |
| `sites.tar.gz`, `functions.tar.gz` | the **live** frontend and functions versions (`v<N>`), when present. Older versions are not kept: they can be rebuilt from the app's repository by its CI, and a daily copy of every version would grow without bound. After a restore, a rollback to a version missing from the backup is refused (its files are gone) |
| `storage.tar.gz` | the app's Storage files (`<storage>/<bucket>/<slug>/`), when it has any |
| `storage-xattrs.json` | their extended attributes: Storage's file backend keeps each object's content type and cache control in `user.supabase.*` attributes, which tar does not carry. Read and written in the Storage container with its own `fs-xattr` module (`STORAGE_CONTAINER`, `STORAGE_CONTAINER_DATA_DIR`). Best effort: when Storage is down, the backup is taken without them (`storage_xattrs: false` in the manifest) and restored files are served as `application/octet-stream` |
| `secrets.enc` | the app's keys (JWT secret, anon and service role keys, role passwords) and its function secrets, encrypted with the platform master key (AES-256-GCM, as the `settings` and `app_secrets` values). Without them, a restored app would get new keys (its deployed frontend, which embeds the anon key, would break) and its functions no secrets. A backup is therefore only restorable with the same `PLATFORM_MASTER_KEY`: keep a copy of it outside the platform host |
| `manifest.json` | what was backed up (no secret): slug, name, live versions, auth policy (`configure_auth`), members (emails and roles), repository link, file sizes |

**Kinds.** `scheduled`: the daily run, every running, stopped or failed app, one at a time; `manual`: `create_backup` (MCP, owner or admin), "Backup now" in the admin console, CLI `backup-app`; `pre_restore`: taken by a restore before it replaces the app's data; `final`: `delete_app` (B8), before anything is removed (if it fails, nothing is deleted). One backup or restore runs at a time across the control plane and the CLI (a session-level advisory lock; a manual backup waits up to 15 minutes for the running one).

**Where.** Without an S3 target, on the `backups` volume (`/data/backups` in the control plane, `BACKUPS_DIR`; the Docker volume `plat_backups`): a lost host loses them too. With an S3 target, each backup is written to the volume, uploaded to `s3://<bucket>/<prefix>/<slug>-<timestamp>/`, then removed locally (the volume is only the staging area). A failed upload makes the backup `failed` (nothing kept, neither locally nor on the bucket). Backups already taken stay where they were when the target changes; a restore reads an S3 backup with the current S3 settings (same bucket).

**Schedule and retention** (settings, overridden at runtime with `set-setting`, see [Settings](#settings)):

| Key | Environment | Default | |
|---|---|---|---|
| `backup_enabled` | `BACKUP_ENABLED` | `true` | the daily run |
| `backup_hour` | `BACKUP_HOUR` | `2` | the run starts at or after this hour, **UTC**, once per UTC day (checked every `BACKUP_CHECK_INTERVAL_SECONDS`, 300). The claim is recorded in `backup_state`: one run per day across processes and restarts; a platform started after that hour runs the day's backups at once. A run interrupted by a restart is not resumed that day (its `running` rows become `failed` at the next start, and the dashboard lists the apps without a backup for 36 h) |
| `backup_keep_daily` | `BACKUP_KEEP_DAILY` | `7` | scheduled backups kept per app: the newest of each of the last N days that have one... |
| `backup_keep_weekly` | `BACKUP_KEEP_WEEKLY` | `4` | ...plus the newest of each of the last M ISO weeks (UTC) that have one |
| `backup_manual_retention_days` | `BACKUP_MANUAL_RETENTION_DAYS` | `30` | manual and pre-restore backups |
| `backup_final_retention_days` | `BACKUP_FINAL_RETENTION_DAYS` | `90` | final backups: a deleted app can be restored during that time |
| `backup_s3_endpoint` | `BACKUP_S3_ENDPOINT` | empty: no S3 | scheme, host and port only: `https://s3.eu-west-3.amazonaws.com`, `https://<account>.r2.cloudflarestorage.com`, `https://s3.fr-par.scw.cloud`... An empty row turns off a target set in the environment |
| `backup_s3_bucket` | `BACKUP_S3_BUCKET` | empty | an existing bucket; S3 is used only when the endpoint, bucket, key id and secret are all set |
| `backup_s3_region` | `BACKUP_S3_REGION` | `us-east-1` | the signing region |
| `backup_s3_access_key_id` | `BACKUP_S3_ACCESS_KEY_ID` | empty | a key limited to that bucket (and prefix): `PutObject`, `GetObject`, `ListBucket`, `DeleteObject` |
| `backup_s3_secret_access_key` | `BACKUP_S3_SECRET_ACCESS_KEY` | empty | stored encrypted with the master key; never printed (`secret_access_key_set`); `set-setting backup_s3_secret_access_key -` reads it from stdin |
| `backup_s3_prefix` | `BACKUP_S3_PREFIX` | empty | key prefix, e.g. `platform/backups` |
| `backup_s3_path_style` | `BACKUP_S3_PATH_STYLE` | `true` | `<endpoint>/<bucket>/<key>` URLs; `false`: virtual-hosted (`<bucket>.<endpoint host>`) |

The retention runs after each daily run (and with `prune-backups`): expired backups are deleted from the volume or the bucket, and their rows removed (audited `prune_backups`); failed attempts are forgotten after 30 days. Configure the bucket's own lifecycle rules (if any) longer than the platform's retention. The S3 client (`src/s3.ts`, SigV4 by `aws4fetch`) uploads each file in one streamed `PUT` (5 GB per file at most, TECH_DEBT CP-20) and makes up to three attempts on 5xx and network errors. Behind an HTTP proxy, set `NODE_USE_ENV_PROXY=1` and `HTTPS_PROXY` in the control plane's environment, with a `NO_PROXY` listing the internal services (`db,caddy,storage,realtime,pooler,studio,edge,control-plane,plat-*`).

**Failures.** A failed backup keeps its row (`failed`, `error`), is listed in the admin dashboard (failures of the last 7 days, the Backups card: failures, apps without a backup for 36 h) and the Backups screen, and is audited per app (`backup_failed`). After a daily run with failures, every active admin gets one email through the platform SMTP ("Backups failed for N apps", each app with its error).

**Restore** (admin only: admin console "Restore…", or `restore-app <backup-id> --confirm <slug>`; audited `restore_app`, or `restore_app_failed`). The confirmation repeats the slug. Two cases:

- *the same app* (the backup's app exists): a `pre_restore` backup of the current state is taken first (unless unchecked, CLI `--no-safety-backup`); the app is stopped (maintenance page), its Realtime tenant removed and its schema relay closed;
- *a deleted app* (its row is gone, e.g. from its final backup): the app is recreated with the same slug, name, keys (its deployed frontend keeps working), repository link and members (accounts that still exist; the backed-up owners, else the restoring admin, own it). The slug must be free. The deleted app's backups belong to it again. If the restore fails, the half-created app is deleted (no backup) so that it can be retried.

Then: the keys, function secrets and auth policy of the backup are put back; the dump is restored with `pg_restore --exit-on-error` (as `supabase_admin`, ownerships and grants included) into a fresh database `app_<id>_restore` created from `template0`, which then replaces the app's database (connections refused, sessions terminated, renamed, the old one dropped). From `template0` rather than `template_supabase`: the dump holds every object (extensions, event triggers, publications, `auth`, `storage`, `realtime` and `_platform` schemas) and restores into an empty database with an identical schema and data (checked on a seed app), while the app's roles and the global roles (`anon`, `authenticated`, `service_role`, `supabase_realtime_admin`) are those of the same cluster. The platform's DDL event trigger is created last by `pg_restore`, so the restore is not recorded as schema changes. The live frontend and functions versions are put back and made live (their `deployments` rows updated, or recreated for a deleted app: the next deployment continues the numbering), the Storage files replaced, then `provision()` re-applies the grants and the read-write setting, recreates GoTrue and PostgREST, the Storage and Realtime tenants (whose migrations are already in the restored database), the routes and the Studio project: the app ends `running`. A failure before the database is replaced leaves the app as it was (restarted if it was running); after, the app is `error`, and the `pre_restore` backup holds the state from before.

Restoring into **another** app (cloning an environment, ARCHITECTURE §3.9) is not available (TECH_DEBT CP-21).

**Operations.**

```bash
docker exec plat-control-plane node src/cli.ts list-backups [<slug>]                    # newest first, deleted apps included
docker exec plat-control-plane node src/cli.ts backup-app demo                          # manual backup now (JSON: id, location)
docker exec plat-control-plane node src/cli.ts restore-app <backup-id> --confirm demo   # pre_restore backup, then the restore
docker exec plat-control-plane node src/cli.ts run-backups [<slug>...]                  # the daily run now (exit code 1 on a failure); with slugs, those apps only, not recorded as the daily run
docker exec plat-control-plane node src/cli.ts prune-backups [--now 2026-11-01T03:00:00Z]   # the retention alone (--now: simulated date)
docker exec plat-control-plane node src/cli.ts set-setting backup_s3_endpoint https://s3.eu-west-3.amazonaws.com
docker exec plat-control-plane node src/cli.ts set-setting backup_s3_bucket acme-platform-backups
docker exec plat-control-plane node src/cli.ts set-setting backup_s3_region eu-west-3
docker exec plat-control-plane node src/cli.ts set-setting backup_s3_access_key_id AKIA...
docker exec -i plat-control-plane node src/cli.ts set-setting backup_s3_secret_access_key - < s3-secret.txt
docker exec plat-control-plane node src/cli.ts set-setting backup_s3_prefix platform/backups
docker exec plat-control-plane node src/cli.ts run-backups                              # check the target: every app backed up to S3
```

Without the control plane (disaster recovery, a backup copied by hand): `pg_restore --list database.dump` shows the content; the dump restores into a database created from `template0` once the app's roles exist (`create role app_<id>_owner` etc., see `packages/sql`), and `secrets.enc` decrypts with the master key (`decrypt()` of `src/crypto.ts`). The simplest path is to put the directory back on the `backups` volume, insert its `backups` row (`kind`, `slug`, `status = 'succeeded'`, `location`) and use `restore-app`.

Local installs: `install.sh` starts a SeaweedFS S3 store (service `s3`, profile `s3-test`, `http://s3:8333`, access key `platform-test`, secret `S3_TEST_SECRET_KEY` of `deploy/.env`) used by the backups e2e suite; the platform keeps its backups on the volume until the `backup_s3_*` settings point to it.

## Load metrics

The control plane samples every app's load into `app_metrics` (`src/metrics.ts`, ARCHITECTURE §4) every minute (`METRICS_INTERVAL_SECONDS`, first sample 10 s after startup), into the row of the current UTC hour:

| Column | Source |
|---|---|
| `requests`, `responses_5xx` | Caddy's access log of the public server: every request whose host is `<slug>.<APPS_DOMAIN>` (frontend, `/auth/v1`, `/rest/v1`, `/functions/v1`), counted in the hour of the request. 5xx responses include upstream errors (502 when a container is down) and functions answering 5xx; the 503 maintenance responses of a stopped app count as requests, not as errors (the router tags them with `platform_maintenance`). Requests of edge functions to their own app through the internal server are not counted |
| `db_size_bytes` | `pg_database_size` of the app database (latest value of the hour) |
| `memory_bytes` | Docker stats of `plat-<slug>-auth` and `plat-<slug>-rest` (usage minus inactive page cache, as `docker stats`), 0 while stopped. The edge runtime is shared by every app: its memory is not attributed |

`apps.last_request_at` keeps the last request seen, beyond the retention (`metrics_retention_days`, 30 days by default: older rows are deleted at each sample).

**Access log.** At startup the router configures (once, idempotently) a Caddy logger `platform_access` that writes the public server's requests as JSON into the `caddy-logs` volume (`/var/log/caddy/access.log` in Caddy, `/data/caddy-logs/access.log` read-only in the control plane), rotated by Caddy at 20 MB with 5 files kept, uncompressed. The API, admin and Studio hosts are skipped, and the entries keep only what the counters and `get_logs` need: host, path (the URI without its query string, where tokens and `apikey` travel), status, time, method, size, duration. No headers (cookies, `apikey`, `Authorization`), no client IP. `get_logs` with `service: "requests"` (and the console's Logs tab) lists an app's requests from the last 16 MB of the current and rotated files: `GET /rest/v1/todos 200 12 ms`. The generic routes (TT-4) serve every app, so the counts come from the request's host rather than from per-app routes; Caddy's own metrics have no reliable per-host label for hosts matched by a regular expression.

**Sampler.** The log is read incrementally from the position stored in `metrics_state` (inode and offset): complete lines only, at most 64 MB per sample, and after a rotation the end of the previous file is read first (found by its inode). The cursor and the counters are committed in one transaction under an advisory lock, so the in-process timer, the `sample-metrics` CLI and `POST /api/metrics/sample` never count a line twice. If the log rotates twice between two samples (more than 20 MB of requests in a minute), the lines of the lost file are not counted and a warning is logged.

**Abandoned apps (A6).** An app is flagged `abandoned` when its last activity, the latest of its last request, its last release, its creation and its last restore from a backup, is older than `abandoned_after_days` (30 by default; `set-setting abandoned_after_days 60`). Requests are only known since the first sample (`metrics_state.started_at`): right after an upgrade, no app is flagged before that many days of data. The flag is shown in the admin console. With the platform SMTP, the owners (active accounts) are emailed once per transition (M6, `src/abandoned.ts`): after every sample, an app that is now abandoned and not yet notified gets a notice ("Your app ... looks abandoned": last activity, what the admin may do, how to keep it), recorded in `apps.abandoned_notified_at` and audited (`notify_abandoned`, with the recipients); the date is cleared when the app is active again, so that a later abandonment is notified again. Stopped apps are not notified. Without SMTP nothing is sent nor recorded: the owners get the notice once an admin configures it. A failed send is retried at the next sample.

App roles: a `collaborator` deploys, inspects the app and manages its users; an `owner` can also manage members, stop, start and delete the app; platform admins can do everything on every app. Memberships created with the former `developer` role are renamed `collaborator` by the idempotent schema migration run at startup.

Membership changes apply to open Studio sessions and PATs on their next request: Studio forward auth and MCP read the user's apps from the database on every request. Member changes are recorded in `audit_log` (`add_member`, `remove_member`), with the acting user for MCP calls and no user for the CLI, which acts as the operator. An identical `add_member` (same role) changes nothing and is not audited.

Membership emails (B7, M6, `src/members.ts`, text in `src/member-mail.ts`): with the platform SMTP, every membership change through MCP, the admin console or the CLI emails the member. When added: who added them (the actor's name and email, "A platform admin" for the CLI), the app's name and URL, the role and what it allows, the Studio link to the app, and that Claude Code with the platform plugin now sees it. A role change sends a short notice with the new role; a removal a short notice that the access is gone. Nothing is sent for an identical add, to a disabled account, to the actor themselves (an admin adding themselves), or without SMTP. A failed send is logged and never fails the change; the `add_member` and `remove_member` audit entries record `email_sent` (and `previous_role` for `add_member`). The emails carry no token nor secret. `add_member` and `remove_member` (MCP and CLI) refuse any change that would leave the app without an owner; through MCP, only an owner of the app or an admin can call them, and the target account must already exist.

Stopping and deleting (journey B8): `stop_app`, `start_app` and `delete_app` are reserved to an owner of the app or an admin. All three write `audit_log` entries and `stop_app` / `start_app` are idempotent (`changed: false`).

- **Stop.** `stop_app` first switches the app to a 503 maintenance response (its `.stopped` routing marker) (HTML page, or `{"code":"APP_STOPPED"}` on `/auth/v1`, `/rest/v1`, `/functions/v1`, `/storage/v1` and `/realtime/v1`), then stops the `plat-<slug>-auth` and `plat-<slug>-rest` containers, so functions cannot run either (the edge is only reachable through those routes). The stopped PostgREST container shows `Exited (255)`: upstream PostgREST exits with 255 on `SIGTERM` after a clean shutdown, not an error. It then makes the app **read-only**: `alter database app_<id> set default_transaction_read_only = on`, and terminates the sessions of the app's own roles (owner, authenticator, auth admin: Studio's pg-meta, functions) so that their next session gets the setting; the platform's admin sessions opt out with `-c default_transaction_read_only=off`. Finally `apps.status = 'stopped'` (shown by `whoami`, `list_apps` and `get_app`).
- **Read-only.** One guard (`requireWritable` in `apps.ts`) refuses every write of a stopped app with `APP_STOPPED: app "<slug>" is stopped and read-only, <action> is refused`: `execute_sql` with `write`, `apply_migrations` without `dry_run`, `set_secrets`, `create_deployment`, `finalize_deployment`, `rollback`, `begin_release`, `link_repo`, `configure_auth`, the app user writes (`invite_user`, `delete_user`, `ban_user`, `unban_user`), and the CI API's publishing requests (409). Reads (including `list_auth_users`), `execute_sql` without `write`, migrations `dry_run` (run in an explicit `begin read write` transaction, always rolled back), logs, `get_app`, members, `start_app` and `delete_app` stay available. In Studio, reads work and SQL editor or table editor writes fail with `cannot execute ... in a read-only transaction`. This is a guardrail, not a security boundary: a session of the owner role can still opt out with `SET` or `BEGIN READ WRITE` (an accepted trade-off, see TECH_DEBT "Accepted trade-offs"). At control plane startup, `syncAll` re-applies the maintenance routes and the database setting from `apps.status`; `create_app` refuses a stopped app.
- **Start.** `start_app` resets the database setting, then re-runs the idempotent provisioning (containers restarted, routes restored, status `running`). An upload made before the stop can be finalized once started.
- **Delete.** `delete_app` is irreversible and requires `confirm` to repeat the slug. It reuses `deleteApp` (as the `delete-app` CLI), which first takes a **final backup** (kind `final`, see [Backups](#backups): database dump, Storage files, live frontend and functions, encrypted secrets, manifest; on the volume or the S3 target). If the backup fails, nothing is deleted. The tool returns the backup's location and id, and the `delete_app` audit entry keeps the slug, the location, the backup id and the file sizes in `details` (its `app_id` becomes null when the app row is deleted). Final backups are kept `backup_final_retention_days` (90 by default), and an admin can recreate the app from one (same slug, keys and data). `backup: false` (CLI: `delete-app <slug> --no-backup`) skips the final backup, with the same rights (owner or admin) and the same confirmation: the data is lost for good, and the audit entry records `backup: null` and `backup_skipped: true` (`false` when a backup was taken).

The e2e suites never touch existing apps or users. Each run creates disposable resources named after a run id: one app `e2e-<id>` for `e2e` (plus `e2e-<id>-ci` and its owner and collaborator for the CI suite, `e2e-<id>-cli` for the `platform-deploy` suite, `e2e-<id>-plg` and its builder for the plugin suite, `e2e-<id>-adm` and two builders for the admin API suite, `e2e-<id>-ui` and its builder for the admin console smoke test, `e2e-<id>-met` for the metrics suite, `e2e-<id>-sa` / `e2e-<id>-sb` for the Storage and Realtime suite, `e2e-<id>-pool` for the pooler suite, `e2e-<id>-mail` and its owner and collaborator for the email suite, `e2e-<id>-sso` and its builder, an admin and a just-in-time account `@sso.example.com` for the SSO suite, `e2e-<id>-bk` and its owner and collaborator for the backups suite, `e2e-<id>-oa` / `e2e-<id>-ob` and their builder for the OAuth suite), two apps `e2e-<id>-a` / `e2e-<id>-b` and two builders `e2e-<id>-alice@example.com` / `e2e-<id>-bob@example.com` (random passwords, kept in memory) for `e2e:studio`. They are deleted at the end of the run, even when a test fails, with `delete-app --no-backup`, then `delete-user` (after the apps: a user who created an app cannot be deleted while it exists); the `after` hook then checks that nothing is left (platform rows, sessions, tokens, memberships, containers, sites directory with its routing marker, database and roles, Storage and Realtime tenants, Storage files) and fails the suite otherwise. The CI suite (`test/ci.e2e.test.ts`) acts as a fake GitHub OIDC issuer: it generates an RS256 key pair, sets `oidc_issuer`, `oidc_jwks` and `ci_allowed_workflows`, toggles `direct_deploy`, and restores the previous settings in its `after` hook. It expects `DIRECT_DEPLOY=everyone` and `ALLOW_TEST_OIDC_JWKS=1` in the environment (local install). The `platform-deploy` suite (`test/deploy-cli.e2e.test.ts`) uses the same fake issuer, and also serves its tokens on a local `ACTIONS_ID_TOKEN_REQUEST_URL`, so that the CLI runs unchanged as in GitHub Actions. Every suite first waits for the control plane to answer through Caddy (`waitForControlPlane`), so it can start right after `docker compose up` returns. Suites that change settings must not run concurrently (two runs at once overwrite each other's issuer, and can restore each other's values). `e2e` test 12 deletes its app with the final backup (checked with `pg_restore --list`) and test 13 deletes a second app (`e2e-<id>-nb`) with `backup: false` and checks that no backup directory is created; the cleanup also removes the run's own backups (`/data/backups/<slug>-*`). The metrics suite (`test/metrics.e2e.test.ts`) sends traffic to its app (a function answering 200, one answering 500, PostgREST 404s, maintenance responses while stopped), forces samples through `POST /api/metrics/sample` and checks the exact counts; for the abandoned flag it backdates its own app and, for the duration of the test, `metrics_state.started_at`, and restores it and `abandoned_after_days` in its `after` hook. **Emails** (M6): the suites expect the local install's SMTP (`SMTP_HOST=mailpit`) and read the emails from mailpit's API (`http://localhost:8025`, `MAILPIT_URL`; `test/mailpit.ts`), searching by recipient: the run's addresses are unique. `e2e` confirms its users' sign-ups (U1), accepts an emailed invitation (B5) and checks the email of a member added with `add_member`, sent once (B7); `test/auth-email.e2e.test.ts` covers sign-up confirmation, password reset with supabase-js (U4), invitations and `configure_auth` (B6) on its own app; the admin suite checks the welcome email, the membership emails (added, role changes, removed) and the auth section of the app page, the metrics suite the abandoned-app notice (once per transition). Suites whose app users need a session at once (`storage-realtime`, `deploy-cli`, the seed) call `configure_auth(email_confirmation: false)` on their app. The path without SMTP (auto-confirmation, invitation link returned) is covered by the unit tests of the GoTrue environment only (`test/auth-policy.test.ts`): switching the platform SMTP off would recreate every app's GoTrue. **Company SSO** (M6 part 2): `test/sso.e2e.test.ts` points the SSO settings at the local mock IdP (`plat-idp`, profile `sso-test`, see [Company SSO](#company-sso)) and restores them at the end; it drives the browser's redirects with `fetch` (the mock signs in the `login_email` of the authorization request, and can tamper with the ID token: `tamper=nonce|aud|iss|signature|expired`). It covers Studio and admin console logins, refusals (domain, unverified email, unknown user, just-in-time creation, state, missing cookie, nonce, signature, audience, issuer, expiry, code replay, another subject), the password policy, and an app's users signing in with `signInWithOAuth({ provider: "custom:company" })` and PKCE. The admin console smoke test also saves the SSO screen and signs in through the mock IdP's form. **Backups** (M7): `test/backups.e2e.test.ts` (`pnpm e2e:backups`) needs the local install's S3 store (`plat-s3`, profile `s3-test`, `S3_TEST_SECRET_KEY` in `deploy/.env`) and Mailpit.
