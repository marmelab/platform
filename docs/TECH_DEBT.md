# Tech debt and known limitations

Single list of the technical debt and known limitations of the platform, checked against the code on 2026-10-06 (M7 part 2: production install, upgrades, security linter; manual test campaign; browser sign-in for Claude Code).
Missing features (❌ and 🟡 items) are tracked in [USER_JOURNEYS.md](USER_JOURNEYS.md), not here.

**Priorities**

- **P1**: security issue, or blocks a production deployment.
- **P2**: robustness, operations or scaling.
- **P3**: comfort or cleanup.

**Updating this file**: add an entry when you accept a debt, remove it when it is paid off. IDs are stable: never
reuse a removed ID. Effort is in days when known.

## Security (cross-cutting)

| ID | Issue | Impact | Suggested fix | Effort | Priority | Source |
|---|---|---|---|---|---|---|
| SEC-1 | The edge runtime shares the `plat` network with Postgres, GoTrue, PostgREST, the control plane (including its internal `:3001` listener) and Studio. Outbound network from functions is fully open (`allow_net: []`). | A compromised or malicious function can reach `db:5432` (with its app's owner credentials only), scan internal services, and call `control-plane:3001` and `studio:3000` (protected only by the config token and the header signature). | Put the edge on a dedicated network with Caddy and Internet egress only; functions already reach their app through `SUPABASE_URL` (internal Caddy). `deny_net` by hostname is not enough (IP bypass). | 0.5–1 | P1 | [M1 §4.8](../spikes/m1-edge-functions/REPORT.md), [M2](../spikes/m2-control-plane/REPORT.md), [M0ter](../spikes/m0ter-studio-builders/REPORT.md) |
| SEC-2 | The Docker socket is mounted in the control plane. | Equivalent to root on the host if the control plane is compromised. | Filtering socket proxy (containers with `platform.*` labels, allowed images only), or a separate orchestrator agent. | 1 | P1 | [M2](../spikes/m2-control-plane/REPORT.md) |
| SEC-4 | `postgres` keeps `CREATEROLE` and `BYPASSRLS`, and the `app_*` roles are not in `supautils.reserved_roles` (verified on `plat-db`). | Whoever holds the `postgres` password can reset any `app_<id>_owner` password and connect to any app database. | Remove `CREATEROLE` from `postgres` at bootstrap (the control plane uses `supabase_admin`), or reserve the `app_*` roles. | 0.5 | P2 | [M0 rec. 4](../spikes/m0-tenancy/REPORT.md), [M2](../spikes/m2-control-plane/REPORT.md) |
| SEC-5 | Studio Settings > API keys shows the app's `service_role` key (as upstream Studio does). | Since the owner no longer has `BYPASSRLS`, the key gives a builder more than the database: GoTrue's admin API (all `auth` tables) and PostgREST as `service_role`. | Hide or mask the key in the policy and the fork UI. | 0.5 | P2 | [M0ter](../spikes/m0ter-studio-builders/REPORT.md), [M0bis](../spikes/m0bis-studio/REPORT.md) |
| SEC-6 | The `platform_session` cookie is forwarded to Studio, and from there to pg-meta (`constructHeaders`). | The platform session token reaches components that do not need it (fork code, pg-meta logs). | Delete the `Cookie` header in the Caddy Studio route after the forward auth (the identity travels in the signed `X-Platform-*` headers). | 0.1 | P2 | [M0ter](../spikes/m0ter-studio-builders/REPORT.md) |
| SEC-7 | `SUPABASE_DB_URL` in functions uses the app's owner role. | A compromised function gets DDL rights and bypasses RLS on the app's `public` tables. | Dedicated `app_<id>_fn` role with DML only. | 0.5 | P2 | [M1 §6](../spikes/m1-edge-functions/REPORT.md), [M2 rec. 3](../spikes/m2-control-plane/REPORT.md) |
| SEC-8 | Per-token restrictions (`tokens.scopes`, `tokens.app_ids`) are enforced (`appForUser`, `appsForUser`, tool registration in `buildMcpServer`) but only deploy tokens use them (`create_deploy_token`: one app, the tools of `platform-deploy`). PATs cannot be restricted from the admin console, and a Claude Code connection (OAuth) has the full rights of its account: there are no OAuth scopes per tool. | A leaked PAT, or the OAuth tokens of a builder's keychain, can do everything the account can on all its apps. | Scopes and apps on PAT creation (admin console); OAuth scopes (read-only, deploy, admin) advertised in the metadata and checked by tool; Claude Code pins them with `oauth.scopes`. | 0.5 | P2 | [M2](../spikes/m2-control-plane/REPORT.md), `apps/control-plane/src/token-scopes.ts` |
| SEC-9 | The master key (`PLATFORM_MASTER_KEY`) lives in `deploy/.env`, with no rotation and no re-encryption of `apps.secrets_enc` and `app_secrets`. | A leaked key cannot be rotated without manual work. | Key id in the ciphertext, rotation command that re-encrypts all secrets. | 1 | P2 | [M2](../spikes/m2-control-plane/REPORT.md) |
| SEC-10 | Runtime settings (`settings` table, `set-setting` CLI) override the environment, including `oidc_issuer` and `ci_allowed_workflows`. `set-setting` and `unset-setting` are audited (`set_setting`, `unset_setting`, secrets as `(secret)`) but without an actor (CP-8); the admin console's Settings screen shows the values in effect and the overrides, read-only. The test-only `oidc_jwks` (inline JWKS trusted by the CI API) is now honoured, and accepted by `set-setting`, only when the control plane runs with `ALLOW_TEST_OIDC_JWKS=1` (written by `install.sh` for local installs only). Since M6 part 2, the same applies to the `sso_*` settings (company SSO issuer, client, discovery URL), set from the admin console (audited, `update_sso`) or the CLI. | Whoever can write the `platform` database or run the CLI can point `oidc_issuer` at an issuer they control, or set `direct_deploy` to `everyone`. Same level as database write access, which already allows minting PATs. A production install that reuses a local `deploy/.env` keeps `ALLOW_TEST_OIDC_JWKS=1`. With the `sso_*` settings, they can also make the platform trust an identity provider they control, and sign in to Studio or the admin console as any account. | Settings changes from the console, with their actor (CP-8). The production installer (M7 part 2) already removes `ALLOW_TEST_OIDC_JWKS` from `deploy/.env`, unsets `oidc_jwks` and warns about a `direct_deploy` override. | 0.25 | P2 | `apps/control-plane/src/settings.ts` (M3bis) |
| SEC-11 | Login throttling (former SEC-3, `src/login-limit.ts`) keeps its counters in the control plane's memory: a restart forgets them, and several control plane instances would each count separately. The per-IP limit uses the address Caddy saw: behind another proxy or a load balancer in front of Caddy, every client would share that proxy's address. | Fine for the single-VM deployment (PLAN_1 §9). | A shared store (table or Redis) for a multi-instance control plane; Caddy `trusted_proxies` (and the matching `TRUSTED_PROXIES`) when a load balancer is added in front of it. | 0.25 | P3 | `apps/control-plane/src/login-limit.ts` |
| SEC-12 | `/rest/v1` and `/auth/v1` answer without an `apikey` header: Caddy routes to PostgREST and GoTrue directly, with no gateway checking the key as Kong does in Supabase. A request without a key runs as `anon` (PostgREST) or reaches GoTrue's public endpoints. Storage and functions require an `Authorization` header. | No privilege gained, since the anon key is public and RLS applies (`[]` on a protected table), but a behaviour difference with Supabase, and no per-key rejection or rate limit at the edge. | A Caddy matcher that answers 401 `No API key found` on `/rest/v1` and `/auth/v1` (except the callbacks and `/verify`, reached by browser redirects) when neither `apikey` nor `Authorization` is set. | 0.25 | P3 | `apps/control-plane/src/router.ts` |

## Browser sign-in for Claude Code (OAuth)

| ID | Issue | Impact | Suggested fix | Effort | Priority | Source |
|---|---|---|---|---|---|---|
| OA-1 | Clients register themselves (dynamic registration, the only mechanism GoTrue offers besides manual clients; it does not support Client ID Metadata Documents): any program on the builder's machine can register, under any name. Only loopback redirect URIs are accepted, and the consent page says the application runs on this computer, but the name it shows ("Claude Code") is self-declared. Registrations are not rate limited (the front uses GoTrue's admin API, whose own dynamic registration is off so that nothing on the internal network bypasses the checks), and unused clients are never deleted. | A malicious local program can ask for the builder's consent under a familiar name; registration spam fills `auth.oauth_clients`. | Client ID Metadata Documents once GoTrue supports them (Claude Code does), with an allow-list of client ids; a per-IP limit on `/oauth/register`; a cleanup of clients without session for 30 days. | 0.5 | P2 | `apps/control-plane/src/oauth.ts` |
| OA-2 | Refresh tokens and GoTrue sessions do not expire on their own (no `GOTRUE_SESSIONS_TIMEBOX` nor inactivity timeout), and a consent stays valid until revoked: the next sign-in of the same account with the same client skips the consent page. | A connection on a lost or shared machine stays usable until an admin revokes it or disables the account. | Inactivity timeout (30 days) and timebox (90 days) on the platform's GoTrue (`authenticate` already checks `not_after`); a "my connections" page for builders. | 0.25 | P2 | `apps/control-plane/src/platform-auth.ts` |
| OA-3 | Refresh token reuse: GoTrue answers the parent of the current refresh token with the current one (its tolerance for concurrent refreshes and lost answers), without revoking anything; only an older token revokes the family. | A refresh token stolen just before its legitimate use gets the current pair instead of being detected. | Accepted GoTrue behaviour; a reuse interval of 0 already removes the grace period after a revocation. Revisit if GoTrue makes it configurable. | – | P3 | `apps/control-plane/test/oauth.e2e.test.ts` (test 5) |
| OA-4 | The platform's GoTrue (`plat-oauth:9999`) is on the `plat` network (SEC-1): a function can call its public endpoints directly, e.g. `/oauth/token` without the front's checks (codes exchanged within 60 s, active account). Codes still need the PKCE verifier, and `authenticate` refuses any token of a disabled account or revoked connection. | No escalation found, but the front is not the only door. | Dedicated network for the edge runtime (SEC-1). | – | P3 | `apps/control-plane/src/oauth.ts` |
| OA-5 | The deploy token reaches `platform-deploy` through Claude: `create_deploy_token` returns it to the model, which passes it as `PLATFORM_DEPLOY_TOKEN=<token>` in the Bash command (allowed by the skills' `allowed-tools`). It shows in the transcript and the command line. | Valid 15 minutes, one app, the publishing tools only, revoked with the connection; still a credential in the transcript. | A handoff the model never sees: e.g. `platform-deploy` requesting the token itself through a local helper of Claude Code, if one becomes available. | 0.5 | P3 | `plugin/skills/deploy/SKILL.md` |
| OA-6 | Local installs: Claude Code only sends token requests over HTTPS or to a loopback host, so on plain HTTP `*.localhost` the token endpoint is announced as `http://localhost:8100/oauth/token` and Caddy routes `localhost` (that path only) to the control plane. | A second public host name on local stacks. Production (HTTPS) is unaffected. | None needed; a local stack with `TLS_MODE=internal` and Caddy's CA trusted by Node would avoid it. | – | P3 | `apps/control-plane/src/config.ts` (`loopbackTokenHost`) |
| OA-7 | `check-connection.sh` cannot see Claude Code's OAuth tokens (keychain): without a PAT it only tells "platform reachable", and the skill tells "not signed in" from "account refused" by whether the platform tools worked earlier in the conversation (`--after-auth-error`). | After a revocation in a new conversation, the builder is told to sign in; the login or the consent page then shows the refusal. | A `/oauth/status` endpoint is not possible without a credential; acceptable. | – | P3 | `plugin/skills/deploy/scripts/check-connection.sh` |

## Company SSO (M6 part 2)

| ID | Issue | Impact | Suggested fix | Effort | Priority | Source |
|---|---|---|---|---|---|---|
| SSO-1 | OpenID Connect only: no SAML 2.0, neither for the platform's logins nor for the apps (GoTrue's SAML, `GOTRUE_SAML_ENABLED` and `/admin/sso/providers`, is not wired). | A company whose IdP only speaks SAML (some ADFS setups) cannot use the company SSO; most IdPs (Entra ID, Google, Okta, Keycloak) also speak OIDC. | Apps: enable GoTrue's SAML with a per-app signing key and register the company's metadata through its admin API from `configure_auth`; platform: a SAML SP library in the control plane, or a broker (Keycloak, Dex) in front of the SAML IdP. | 2 | P3 | `apps/control-plane/src/sso.ts`, `src/app-sso.ts` |
| SSO-2 | Every app that enables company SSO uses the platform's OIDC client: the admin must register each app's callback (`<app URL>/auth/v1/callback`, shown by `get_app` and on the SSO screen) at the IdP, which rarely allows wildcards (Entra ID does not). The client secret is copied into each of these apps' `auth.custom_oauth_providers` in clear (GoTrue's `GOTRUE_SECURITY_DB_ENCRYPTION_*` is off): readable by the app's GoTrue role (and `postgres`, SEC-4), not by the owner role (Studio, `execute_sql`, checked by `sso.e2e`). | One admin step per app before its users can sign in (the IdP refuses the unknown redirect URI); a leak of one app's GoTrue role (or its database dump, e.g. any of its backups, CP-19) exposes the shared client secret. | A per-app client set by the admin (admin console, app page) or created through the IdP's dynamic client registration; GoTrue's database encryption with a key derived from the master key. | 1 | P2 | `apps/control-plane/src/app-sso.ts` |
| SSO-3 | GoTrue's custom providers only accept an HTTPS issuer that resolves to a public address (SSRF guard, at configuration and at each discovery refresh). | An IdP on a private network (on-premises Keycloak or ADFS on 10.x) works for the platform's logins but not for the apps' company SSO (`configure_auth` fails with GoTrue's error). The local stack works around it: the mock IdP has a TEST-NET-2 address on its own network, which every app's GoTrue joins, and a test CA they trust (`SSO_TEST_NETWORK`, `SSO_TEST_CA_VOLUME`, local installs only). | For such IdPs, GoTrue's built-in `keycloak` or `azure` provider through the environment (no SSRF guard), or a GoTrue patched to allow listed private issuers. | 0.5–1 | P3 | `apps/control-plane/src/app-sso.ts`, `deploy/docker-compose.yml` (service `idp`) |
| SSO-4 | No link with the IdP after the login: a user disabled at the IdP keeps their platform sessions (up to `SESSION_TTL_SECONDS`, 12 h) and their PATs; no back-channel logout, no SCIM deprovisioning, signing out does not sign out of the IdP (no RP-initiated logout); just-in-time accounts are always developers (no role or group mapping from the IdP's claims). | A leaver must also be disabled on the platform (A5: that ends their sessions and PATs at once). | Shorter sessions for SSO logins, OIDC back-channel logout or SCIM, a group claim mapped to the admin role. | 1–2 | P2 | `apps/control-plane/src/sso.ts` |

## Control plane & MCP

## Accepted trade-offs

Deliberate choices, not debt. Revisit only if the context changes.

- **Separate sign-ins for Studio and the admin console**: both use the platform sessions, but each host has its own
  host-only cookie. A cookie for the parent domain would also reach every `<app>.<domain>`, whose functions are
  written by builders.

- **Edge functions are isolated by V8 isolate**, not by container or process: a V8 or edge-runtime flaw would break
  isolation between apps. Acceptable for code from trusted colleagues; to be documented for clients
  ([M1 §4.9](../spikes/m1-edge-functions/REPORT.md), [PLAN_1 §12](../PLAN_1.md)).
- **The owner role sees every row of its `public` tables**: as the tables' owner it is not subject to their RLS
  (unless `FORCE ROW LEVEL SECURITY`), like Supabase's `postgres`. This applies to `execute_sql`, Studio and
  `SUPABASE_DB_URL`. An owner view or `SECURITY DEFINER` function that reads `auth.users` exposes all its rows; the
  linter flags `security_definer_view` ([M0ter](../spikes/m0ter-studio-builders/REPORT.md)).
- **Cluster metadata is visible across apps**: `pg_database` and `pg_roles` list the other apps' database and role
  names, now also in builders' Studio. Names only, no access to data; inherent to a shared cluster
  ([M0bis](../spikes/m0bis-studio/REPORT.md), [M0ter](../spikes/m0ter-studio-builders/REPORT.md)).
- **`anon`, `authenticated` and `service_role` are global NOLOGIN roles** shared by all apps; grants are per database
  and `SET ROLE` across apps is refused ([M0](../spikes/m0-tenancy/REPORT.md)).
- **A stopped app is read-only by guardrail, not by a hard guarantee** (formerly CP-9, accepted on 2026-10-02): the
  database default `default_transaction_read_only = on` (set by `stop_app`, reset by `start_app`) and the control
  plane's `requireWritable` guard prevent accidental writes (builders, Claude, Studio). A session of the owner role
  (Studio SQL editor, pg-meta) can still opt out with `SET default_transaction_read_only = off`, `BEGIN READ WRITE` or
  `ALTER DATABASE ... RESET` and write deliberately. If a hard guarantee becomes necessary: revoke `CONNECT` from the
  owner role and give Studio a read-only role while stopped, or transfer the database ownership to an admin role
  (`apps/control-plane/src/apps.ts`, B8).
- **Login lockout per email** (former SEC-3, paid off on 2026-10-02 with Studio's CSRF guard): after 5 failures, an account's logins are locked with an exponential backoff
  capped at 15 minutes, from any IP. Anyone who knows an address can therefore delay that account's sign-in by at most
  15 minutes at a time; open sessions and PATs keep working. The alternative (per email and IP only) would let a
  distributed attacker guess without limit.
- **Realtime tenants are created with a temporary superuser** (accepted on 2026-10-03, formerly part of SR-2): Realtime's
  tenant migrations `GRANT` the supautils-reserved `supabase_realtime_admin`, which only a superuser may do. The control
  plane creates each tenant with `platform_realtime_migrator` (superuser, `LOGIN` and a one-time password only for the
  duration of the call, serialized, locked and its sessions terminated right after), reassigns what it created to
  `supabase_realtime_admin`, then switches the tenant to `app_<id>_realtime`. A superuser credential therefore transits
  through Realtime's API and metadata database (encrypted with `DB_ENC_KEY`) for a few hundred milliseconds per tenant
  creation; it is useless once the call returns. Revisit if upstream makes the migrations runnable without a superuser
  ([M5](../spikes/m5-storage-realtime/REPORT.md)).
- **Studio project config cache**: a removed app stays visible for up to 2 s; if the control plane is down, the last
  config is served for up to 30 s ([M0ter](../spikes/m0ter-studio-builders/REPORT.md)).
- **`accept_lints`** lets a builder keep an `ERROR` lint with explicit consent; every acceptance is audited
  ([M2 post-M3](../spikes/m2-control-plane/REPORT.md)).
- **Studio license** (Sustainable Use License): not a blocker as long as the product is not resold
  ([CLAUDE.md](../CLAUDE.md)).
